# Small-core component comparison

Predeclared before model execution. The earlier lifecycle results remain unchanged.

## Questions and scope

Does the smaller default reduce overhead without worse delivered behavior or production-code quality? Compare the same short project guide alone, the previous tack default and the candidate default. All three receive the same product contract, existing checks and short AGENTS.md. Task prompts ask only for the product change. They do not request tests, design practices or workflow. The guide contains the same branch, regression-check, documentation and Conventional Commit preferences in every condition. No condition receives private acceptance checks.

This is a component experiment, not another full lifecycle claim. It reuses the shipment and settings fixtures from the earlier quality study, with two models (Luna and Sol), medium effort and two repetitions: 24 development sessions, at most 300 seconds each, two concurrent calls. Conditions rotate within shuffled matched blocks. Use a pinned product commit and image digest; record archive, fixture and controller hashes before calls. No selective retries or repairs; retain timeouts, provider failures and absent token usage. Stop unscheduled calls after an infrastructure failure.

Eight independent Astra/medium reviews compare anonymous triplets, one per matched block, using the existing six-dimension production-only rubric. Labels and order are randomized outside the reviewer containers. This smaller study does not repeat reviewer order, so score differences remain uncertain. Reviewers get no condition identity, tests, process artifacts, outcomes or cost. The controller checks citations and computes weighted scores. Acceptance and test sensitivity are assessed separately in containers without network, credentials or host mounts. Existing evaluator tests must pass first.

Report time, input/cached/output tokens, failures, acceptance, tests rejecting the original defect, observed branch/commit conventions, independent quality and install time separately. A smaller description catalog is a footprint change, not measured token savings. Do not equate a test file with TDD or a reviewer score with correctness. Lower code quality or more failures cannot be hidden by cheaper successful attempts.

## Targeted verification without model confounding

Test setup-choice checking and prospective merge execution separately without model calls. The plan originally proposed a fourth model condition for targeted verification. A deterministic check can be evaluated directly against actual incompatible/compatible trees; a fourth prompted assistant condition would conflate tool behavior with how explicitly the prompt told it to use the tool. Keep that narrower attribution and avoid another speculative model harness.

Use two consumer incompatibilities: a renamed field and a numeric unit change with no key error. Show branch-specific tests passing, a clean Git merge, a failing combined consumer check and a passing compatible correction. Check read-only Git state, missing checks/dependencies, trust and timeouts. Validate approved setup values, an omitted shared default, a local override and a fresh clone. These prove concrete detections and reproducible configuration checks. They do not prove fewer real-world reviews, human onboarding time, scalable-system maintainability or that an assistant would otherwise overlook the defect.

The user declined the separate real-project pilot. Retain that limitation. Ship useful checks on their measured narrow merits; do not sell the default as a productivity gain unless the comparisons support it.

## Reproduction

`python3 evals/lean.py MANIFEST --dry-run` prints the fixed schedule. Execution requires explicit `--auth PATH --output NEW_DIRECTORY`. Review separately with `--reviews SOURCE` and a new output directory after coding finishes. Only ignored raw evidence contains transcripts. Public reports include complete outcomes and anonymous production bundles; never publish credentials.
