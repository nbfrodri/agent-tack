# Backend/frontend integration pilot

Four Codex sessions completed with no retries: one backend/consumer pair per tack version. **Both pairs passed all seven frozen integration checks. The candidate took 5.5% longer overall.** This exploratory sample does not establish a general quality or productivity improvement.

The useful result was a concrete completion-check defect: an unrelated paused handoff could trigger a request to refresh documentation. It was reproduced offline and fixed after this pilot. The frozen results below do not include that correction or claim its performance effect.

## Conditions and outcomes

The [protocol](2026-10-08-teamwork-protocol.md) fixes prompts, contract, versions and maximum four sessions. Baseline is `f4b88b4`; candidate is `2166cf2` with team coordination selected. Both use GPT-6.1 Sol, medium effort, Codex 0.160.1 and fresh participant homes. Neither prompt asks for tests, engineering practices or handoffs. This compares two tack versions, not tack against a plain project; the previous [quality comparison](2026-10-08-quality-efficiency.md) remains separate.

The original stubs fail all seven. Grading combined the producer's backend and consumer's frontend in an isolated container without network or credentials, after delivery. It used the [published probe](support/probe-teamwork.py); configured smoke/unit checks are separate evidence.

## What the code and workflow show

Both implementations are small and direct: explicit backend validation, integer prices, generated order IDs, an injected frontend transport and useful errors. Both added meaningful tests and preserved form input. There is no basis for a general code-quality winner. Supplemental inspection found different defensive behavior outside the fixed contract: baseline guards a non-object backend payload, while candidate wraps frontend response handling in its transport error boundary. Those observations do not change frozen acceptance.

The baseline consumer inspected the backend ref and fast-forwarded it into its own branch before integration testing. The candidate kept the dependency unmerged, used `tack team` and tested against a local snapshot. Both approaches are valid here. The candidate handoff explicitly recorded base/producer commits, branch-only availability, quantity conversion and remaining work. It also guessed two handoff filenames before finding the actual path; instructions did not eliminate unnecessary exploration.

Both understood that backend work was absent from the integration base and left analytics paused. However, completion reminders still treated the unrelated handoff's branch mismatch as stale task documentation. The assistants made additional documentation commits, and their last replies focused on handoff maintenance instead of the original implementation. These are observed UX costs, not evidence of better coordination.

Follow-up changes in this PR:

- In team projects, a handoff naming another branch no longer triggers a Stop refresh by itself. A regression test fails before the fix and passes afterwards; solo mismatch reminders remain.
- Reply guidance asks for the original task outcome after a hook-driven repair. This instruction change has not been re-benchmarked.
- Separate Windows CI found and corrected bare `bash` selecting WSL during bootstrap. The Linux pilot did not exercise that path.

## Evidence and limits

[Machine-readable facts](2026-10-08-teamwork-facts.json) include every session, observed model/effort, usage, command results, delivery hashes, exact image/product/controller identities and grader outcomes. Local raw evidence is retained at `evals/out/teamwork-20261008/raw-evidence.tar.gz`: 110 files, SHA-256 `9bd7f98e092612ab215291ded90778fd6d638744c70f8ff7558c62b753a92ef5`. It contains no authentication homes or `.git` directories; raw artifacts are not installed by tack or committed into the repository.

One pair per condition, fixed execution order, uncontrolled model latency and a synthetic injected transport limit interpretation. Time excludes installation, transfer normalization and grading, and is not human development time. Review was by the orchestrator; there was no additional blind numeric panel. No real HTTP server, simultaneous pushes, GitHub protection or installation adoption was measured. Bootstrap, branch conflicts and PR policy have separate deterministic regression coverage.

Keep these features for explicit shared setup, inspectable Git evidence and useful integration context. Do not market this pilot as a measured speed or general code-quality gain. No additional sessions were spent trying to turn a null result into a positive one.
