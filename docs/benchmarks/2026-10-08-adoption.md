# Project adoption: shared setup works, quality is tied, overhead remains

Eight complete journeys compared a well-configured native project with tack auto on revision `a54eda9`. Each journey configured an existing service, cloned its committed setup into a new developer home, fixed a bug and added a feature in fresh Codex sessions. Both conditions started with the same useful AGENTS.md, domain contracts and engineering requirements.

**All 16 code tasks passed hidden acceptance checks. Both conditions wrote regression tests that caught every injected fault. Tack transferred the selected context paths, reply style and mode successfully, but took about twice the total session time.** This supports the configuration mechanism; it does not demonstrate a code-quality or productivity gain over good native project guidance.

[Protocol](2026-10-08-adoption-protocol.md) was committed before model execution. [All-run facts, diffs and transcript hashes](2026-10-08-adoption-facts.json) include every attempt. [Code and workflow review](2026-10-08-adoption-quality.md) records findings and limits.

## Observed results

Codex CLI 0.160.1, medium effort, ChatGPT subscription, two repetitions per model/condition, three sessions per journey: **24 completed sessions, no retries, timeouts or infrastructure failures**. Each row below contains two setup sessions and four code tasks. Time is model-session wall time; input includes cached input. These are not USD costs.

| Model | Condition | Correct code tasks | Median setup seconds | Median code-task seconds | Total session seconds | Input / cached / output tokens |
| --- | --- | --- | --- | --- | --- | --- |
| gpt-6-luna | Native project | 4/4 | 38.0 | 27.6 | 191.8 | 912,322 / 780,288 / 10,651 |
| gpt-6-luna | tack auto | 4/4 | 97.9 | 46.3 | 404.6 | 2,906,212 / 2,643,712 / 25,612 |
| gpt-6.1-sol | Native project | 4/4 | 75.2 | 60.1 | 382.3 | 793,213 / 688,128 / 10,419 |
| gpt-6.1-sol | tack auto | 4/4 | 175.5 | 97.0 | 748.5 | 1,848,177 / 1,617,664 / 16,977 |

For this fixed journey mix, tack used **2.11x / 1.96x total session time** and **3.19x / 2.33x input tokens** with Luna / Sol. Excluding the setup session, code-task time was **1.80x / 1.71x** baseline. Most input was cached; neither input ratios nor elapsed time establish a paid-cost ratio. Tack installation itself took 1.62-1.71 seconds per participant, measured separately from the sessions; Node and Codex were already available. These totals do not include a human's decision time or environment preparation.

## What crossed into the second clone

| Observation | Result |
| --- | --- |
| Initial production behavior and existing tests preserved during setup | 8/8 journeys |
| Existing architecture location retained, valid PR template added, setup committed cleanly | 8/8 |
| Declined extra skills/agents not added | 8/8 |
| tack activation and `auto (shared)` mode present in the new clone | 4/4 tack journeys |
| Architecture, plan and handoff paths plus brief replies explicitly read from shared configuration | 4/4 tack journeys |
| New clone initially untrusted; execution authorized separately in that clone | 4/4 tack journeys |
| Conventional Commit preference explicitly pinned in shared configuration | 2/4 tack journeys; both Sol runs |

Both Luna runs documented Conventional Commits in AGENTS.md and inherited tack's `true` default, but omitted the shared setting. The observed effective value was correct. By the documented precedence, a teammate's personal `false` default would win when that shared value is absent: this is a portability gap in the assistant's setup, not a failed JSON transfer. This inference was not a separate model experiment.

The baseline also shared guidance successfully through AGENTS.md and Git. It is not penalized for lacking tack-specific files or executable settings. No run required a fork. Already selected choices were supplied in the prompts, so this experiment does not establish how well an interactive assistant asks questions or saves human onboarding time.

## Verification and engineering evidence

- All 16 tasks showed a failing behavioral test before the first recorded production edit and passing checks afterwards. This event ordering was reviewed; it is narrower than proving every part of a TDD process.
- The grader ran 20 hidden cases after each bug fix and 33 after each feature: 424 case executions, all passing. Cases cover numeric boundaries, original IDs, routing, unknown types and caller preservation.
- Each condition's tests caught 12/12 injected faults across finished snapshots: permissive validation after each task and wrong invoice routing after each feature. These two fault families do not establish general mutation coverage.
- All 24 delivered snapshots had passing public suites and clean Git state. Production changes remained small and modular; no new dependency or speculative abstraction was needed.
- The eight post-delivery `tack verify` runs had all selected commands pass. Six reported `passed`; two reported `incomplete` because newly created plan/log files had no executable checks. Those two results correctly kept the gaps visible; they were not behavioral test failures.

The verifier exposed selected checks and incomplete areas. This batch provides **no observed example of an additional production defect caught only by tack**. The baseline also followed TDD and produced useful tests when given the same project guidance.

## Improvement candidates from this evidence

1. Make guided setup explicitly save each selected shared policy, including choices matching current defaults. Verify effective values **and their origins** in a second clone.
2. Make the common setup path shorter and clearer. Several tack sessions read CLI implementation files or repeatedly inspected modes/help. Compare a simpler path before claiming it reduces overhead.
3. Review check maps for overlapping full/focused suites and distinguish a documentation reminder from a check of documentation content. Do not add irrelevant mappings merely to remove an incomplete status.
4. Keep TDD, pragmatic SOLID, Git discipline and meaningful tests. Measure whether extra instructions, plans and repeated checks improve outcomes over a strong native project baseline before making them mandatory.

These are candidates, not measured causes of the timing difference or implemented product fixes in this benchmark PR. The frozen product was not tuned during the comparison.

## Limits and evidence retention

This is a small synthetic Node service with clear contracts, not a production adoption study. It covers one tool, two models, two repetitions and two simple code changes; it does not establish statistical significance, long-term maintenance gains, editor parity or performance on harder tasks. Quality review was performed by the same assistant, unblinded. External skill installation, live issue/PR publication and interactive user choice were excluded.

The disposable Linux container had no host mounts. Private participant homes and subscription authentication were removed; the product tree hash remained unchanged. Hidden checks stayed outside the model environment until all sessions finished. A detector correction accepts valid uppercase PR-template filenames; the protocol records it and applies it to every run. No behavioral acceptance criterion changed.
