# Small core and executable agreements: mixed costs, no general quality gain

All **24 development sessions and eight independent code reviews** completed without provider failures, retries or timeouts. A short project guide and the smaller tack default each passed the frozen acceptance checks in 8/8 deliveries; previous tack passed 7/8. The smaller default did not improve mean blind code-quality grades. Post-hoc probes found defects beyond acceptance in every configuration.

The functional changes have narrower evidence: approved configuration choices can be checked against saved and effective values, and two independently passing branches can be tested together before changing the source checkout. Neither result establishes less human rework or faster future development in real teams.

## Code and engineering evidence

The previous Luna settings delivery in block 3 treats explicitly supplied `APP_ATTEMPTS=None` as absent instead of rejecting it. That is the single frozen acceptance failure. The other passing deliveries are not defect-free:

- Both Luna small-core settings deliveries and both Luna guide deliveries accept invalid overrides when a later environment value masks them. For example, an invalid boolean attempts override with `APP_ATTEMPTS="3"` succeeds. The contract requires invalid override values to fail. Previous tack rejects those cases. This is a confirmed missing validation boundary, not an inference from test counts.
- In block 7, the guide and small core reject a valid `collections.UserDict` environment. Additional decimal-string probes distinguish Unicode-digit and very long leading-zero handling. Only block 5's three settings implementations pass all of these extra settings probes. These boundary probes were added after review and are exploratory, not a replacement acceptance score.
- All twelve shipment deliveries lose an inherited or non-enumerable original ID when building the output key from a spread copy. Some also accept function inputs. The original implementation already had these weaknesses for created events; the new cancellation path inherits them. These are less typical than plain JSON events and should not be presented as newly introduced high-impact production incidents.
- Reviewer comments about array inputs, invalid non-mapping environment objects and changing exported defaults depend on contract interpretation. Their judgments remain visible; they are not counted as independently confirmed major defects.

All 24 delivered test suites reject the original defective implementation in the separate sensitivity probe. Observed branch creation is 8/8 in each configuration. Tack versions produce Conventional Commits in 8/8 each; the guide produces them in 3/8, leaving the other local deliveries uncommitted. No commit contains AI attribution. These are process observations, not code-quality points or acceptance failures.

Transcript inspection establishes test-first red/green in `0-improved`, `3-improved` and `5-plain`: two small-core deliveries and one guide delivery. The remaining attempts have no demonstrated test-first sequence in this record. Requiring TDD in guidance does not guarantee it, and these three sequences do not establish better code by themselves. Sources and observed commands remain in the public facts; private transcripts are retained locally.

## Concrete verification gains

The seven [integration tests](../../tests/integration-verify.test.py) and [configuration tests](../../tests/project-config.test.py) cover these outcomes without model calls:

| Case | Earlier signal | New executable observation |
| --- | --- | --- |
| Agreed team setting omitted or overridden locally | A configuration listing can show a plausible default | `config --check FILE` exits nonzero and identifies expected, shared and effective values |
| Shared choices in a fresh clone | Personal defaults can differ; trust must remain local | Explicit shared values still match the approved selection; trust is not inherited |
| Alias removal combined with consumer narrowing | The same consumer test passes on each branch; Git merges cleanly | Prospective merge check fails; compatible consumer fix passes |
| Numeric unit change combined with a hardcoded divisor | The same consumer test passes on each branch; Git merges cleanly | Combined result has the wrong amount; verification fails, then passes with the correct scale |
| Dirty input, unknown ref, no checks, absent ignored dependency or timeout | No defensible compatibility result | Explicit failure/unverified result; no green compatibility claim |

The fixture audit strengthened both examples to run the same consumer check independently on each branch, rather than only producer assertions on the backend. This test-only refinement happened after model collection began and did not change any model prompt, product archive, acceptance criterion or delivered code. Linux and native Windows reproduce the stronger fixtures. Source head, refs, index, working tree and object counts remain unchanged by the prospective verification in preservation tests.

The commands automate existing Git/check operations. A developer can perform them manually or use CI/merge queues; they are not unique algorithms, do not predict unseen branches, and cannot find defects missing from the declared checks. Configuration checking also needs an independently approved selection: comparing a profile to itself cannot prove the user's intent.

## Decision and limits

Keep the smaller catalog for its lower installed footprint and retain the two executable checks for their demonstrated detections. **Do not sell this as a general quality or productivity improvement.** The extra workflow cost is not compensated against the short guide in this sample. The four broader goals—fewer escaped defects than capable alternatives, less rework, easier later changes and faster human onboarding—remain unproven.

If a short project guide already works, use [only the CLI checks](../verification.md#use-the-checks-without-installing-ai-guidance) without installing global guidance. Enable additional workflow or capabilities for a concrete project need and measure their cost. Do not add more generic rules or launch repeated model batches merely to seek a favorable result. The user declined the separate real-project pilot; this report makes no claims about that team.

These known small fixtures, two repetitions and one reviewer per block are exploratory. The study does not measure a later feature, human clarification time, real integration incident rates or system scalability. The prior [full lifecycle study](2026-10-08-lifecycle-value.md) remains the evidence for those measured stages and is unchanged.

Reproduce model scheduling with `python3 evals/lean.py evals/batches/lean-core.json --dry-run`. Execution and anonymous reviews require explicit subscription authentication and fresh output directories as documented in the protocol. Generate tables with `evals/lean_report.py`; run supplemental `evals/lean_probe.py` only inside the isolated evaluator. Runtime archives exclude evaluators, reference tests and benchmark reports. Raw evidence identity is recorded in the public facts without publishing credentials or transcripts.
