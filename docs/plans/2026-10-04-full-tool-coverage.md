# Full tool coverage: VS Code setting and Codex agents and hooks

- Status: done; Codex hooks verified against real payloads (the guard turns asks into denials for Codex, which otherwise runs a command when a hook asks), Codex agents generated, VS Code setting automated. Users approve the Codex hooks once with `/hooks`.

## Research (2026-10-04, Codex docs)

- Agents: one TOML per agent in `~/.codex/agents/`; required `name`, `description`, `developer_instructions`; optional `model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`, `skills.config`. The `name` field identifies the agent.
- Hooks: `~/.codex/hooks.json` (or `[[hooks.Event]]` tables in `config.toml`) with the same `{event: [{matcher, hooks: [{type: command, command, timeout}]}]}` shape as Claude Code. Events include `PreToolUse`, `PostToolUse`, `SessionStart`, `Stop`. Common stdin fields: `session_id`, `cwd`, `hook_event_name`; `PreToolUse` sends `tool_name` (`Bash`, `apply_patch`, MCP) and `tool_input.command`.
- Differences that matter: `permissionDecision` accepts only `allow` or `deny` (no `ask`), so the guard must turn `ask` into `deny` with a reason that the user can run the command themselves; exit code 2 blocks with the reason on stderr; `Stop` blocking semantics need a real capture before wiring the Stop check. `SessionStart` accepts `hookSpecificOutput.additionalContext`.
- Verify with a real `codex exec` run that logs each hook's stdin before registering hooks.
- Level: strict (installer, ownership and hooks for another tool)
- Goal: the installer makes every supported tool receive as much of the harness as it can, reversibly; what cannot be automated is reported clearly.

## Workstreams and acceptance criteria

1. **VS Code: load project `AGENTS.md`**
   - When VS Code is detected, set `chat.useAgentsMdFile: true` in the user settings (`~/.config/Code/User/settings.json` on Linux, `~/Library/Application Support/Code/User/settings.json` on macOS; also Insiders and VSCodium paths when present).
   - Only when the file is absent or plain JSON; a file with comments or trailing commas is left untouched with a warning and the manual step. Existing user values are never overwritten.
   - Recorded in the ownership metadata; `uninstall.sh` removes the key only if it still has the installed value; `--dry-run` previews it; `harness doctor --tools` reports it.
   - Toggle: `harness config vscode-agents-md false --global` skips it.
2. **Codex agents**
   - Research first: confirm the agent TOML format and directory (`~/.codex/agents/`) from Codex's documentation and a real `codex` run.
   - Generate one TOML per harness agent from `agents/*.md` (name, description, developer instructions; model hints only when Codex supports them), as generated files with ownership records rather than symlinks, regenerated by every install.
   - Tests for conversion, idempotence, user edits preserved and uninstall.
3. **Codex hooks**
   - Research first: confirm `~/.codex/hooks.json` (or `config.toml`) format and the payload each event sends, with a captured real payload.
   - Register the guard (PreToolUse for shell commands), session context and Stop check only where the payload matches what the scripts read; adapt the scripts through a small input-normalising layer if needed, never by weakening their checks.
   - Merge tagged entries like the Claude settings merge; tests with captured payloads; uninstall reversal.
4. **Docs:** `docs/editors.md`, `docs/how-it-works.md`, `targets.txt` columns (Codex agents and hooks), README tools line, architecture.

## Order and delegation

- 1 → research for 2 and 3 → 2 → 3 → docs. Workstream 1 is independent; 2 and 3 share the Codex research.
- Delegation (strict): one implementer worktree for workstream 1; the main agent owns the Codex research and adapters, which need careful integration with the guard.

## Risks

- VS Code settings are JSONC; a wrong merge corrupts user settings, so comments mean warn-and-skip.
- Codex payload or format changes; the weekly compatibility workflow should exercise the adapters.
- Running the guard under another tool must fail safe: unknown payloads ask or allow per the guard's current fail-open rule, documented.
